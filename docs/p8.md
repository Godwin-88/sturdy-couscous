# P8 — Multi-Asset, Multi-Venue, Overlay Ablation: Capstone Results & Packaging

**Phase goal:** Synthesize everything validated in P1–P7 into the actual research output — the ablation study that answers "does KG-grounding add value, and where" — plus package the system (docs, architecture writeup, reproducibility artifacts) for its three stated end uses: personal live trading record, a portfolio piece for the WorldQuant MScFE capstone/quant job search, and a potential sellable product. This phase produces no new engine code; it consumes everything built so far.

---

## Feature 1: Full Ablation Study Execution

**Description:** Run the complete ablation matrix — KG-grounded vs. ungrounded, each overlay independently on/off, across the full multi-asset (equity/crypto/macro-proxy) and multi-venue (Kraken/IBKR) universe — using the P1/P2 backtest engine, and capture results in the extended metric set from P2.

### User Stories

- As a **capstone author**, I want one comprehensive, reproducible run that answers "is GraphAlpha's KG-grounding adding statistically significant value, and is that value concentrated in a particular asset class or regime," since this is the central empirical claim the whole project rests on.
- As a **researcher**, I want the overlay ablation (news on/off, macro on/off, both on/off, baseline) cross-referenced against the KG-grounded/ungrounded split, so I can attribute performance to the *specific* architectural component responsible — not just "the system" in aggregate.
- As a **future employer/reviewer evaluating this work**, I want the ablation methodology and results presented with the same rigor as a published quant research note — clear hypothesis, clear test, honest reporting of non-significant or negative results.

### Acceptance Criteria

- [ ] The full ablation matrix is executed: {KG-grounded, ungrounded} × {baseline, news-off, macro-off, both-off} = 8 configurations minimum, each producing the complete P2 metric set (Total Return, Sharpe, Calmar, Max DD, Ann. Vol, Profit Factor, Win Rate, Avg Hold Days, Jobson-Korkie).
- [ ] Results are broken down by asset class (equity/crypto/macro-proxy) and by regime, using the breakdowns built in P2 Feature 2 — not reported only as one blended portfolio number.
- [ ] Jobson-Korkie significance is reported per asset class against the asset-class-specific benchmarks (per the earlier decision: SPY for equity, BTC for crypto, etc.), with honest reporting of `p-value`/`significant` even where results are not favorable to the KG-grounded hypothesis.
- [ ] The backtest date range used is documented and justified (e.g. covers at least one full bull/bear/high-vol regime cycle, not cherry-picked to a favorable period) — confirmed by checking the date range against known historical regime transitions, not just picking "the last N years" by default.
- [ ] All configuration (date range, universe, thresholds) used to produce the headline results is captured in a single reproducible config file/script, such that re-running it produces the same numbers (modulo any genuinely stochastic component, which should be flagged if present).
- [ ] Results explicitly distinguish "backtest-only" performance (using the internal fee/slippage model, P1 Feature 7) from anything claiming to reflect live/paper venue behavior — no conflating the two given the documented fidelity asymmetry (main spec §5.6).

## Feature 2: Dual-Engine Parity Evidence Compilation

**Description:** Consolidate the parity/validation evidence generated across P3 (unit parity), P5 (shadow mode), P6 (cross-venue), and P7 (live validation) into a single coherent "this system's two engines agree, and live behavior matches what was validated" narrative and artifact set.

### User Stories

- As a **capstone author**, I want to be able to state "the Python research engine and C++ production engine produce identical sizing decisions, verified to 1e-6 tolerance across N test cases and M live shadow-mode cycles" as a substantiated claim, with the underlying test/log artifacts available to back it up.
- As a **prospective employer or buyer**, I want evidence that this isn't just two systems that happen to look similar, but a system with an actual engineering process for proving consistency between research and production — this is differentiator material for both the job search and the sellable-product framing.

### Acceptance Criteria

- [ ] A single document/artifact compiles: P3's unit parity test suite pass rate and tolerance achieved, P5's shadow-mode discrepancy log summary (count of cycles run, count/nature of any discrepancies found and resolved), P6's cross-venue NAV/drawdown validation results, and P7's paper-vs-live validation period results.
- [ ] Any parity discrepancy ever found during P3–P7 (even if subsequently fixed) is documented with its root cause and resolution — this is more credible than a record showing zero issues ever, and demonstrates real engineering rigor.
- [ ] The compiled evidence is structured so a technical reviewer (e.g. a quant hiring manager) could independently verify the claims by re-running the referenced test suites, not just trust the summary.

## Feature 3: Architecture & Decision-Record Writeup

**Description:** A written document explaining *why* the system is built the way it is — dual-engine split (Python research / C++ execution), multi-venue routing, the overlay architecture — aimed at a technical audience evaluating engineering judgment, not just output metrics.

### User Stories

- As a **capstone author**, I want to explain the reasoning behind the Python/C++ split (research agility vs. production latency/safety) as a deliberate architectural decision, since this is exactly the kind of judgment a quant employer wants to see demonstrated, not just "I used C++ because it's fast."
- As a **future employer**, I want to see the explicit tradeoffs considered (e.g. why IBKR fills use the Gateway's simulator while Kraken paper uses an internal model, and why that asymmetry was accepted rather than hidden) — this signals self-awareness about the system's limitations.

### Acceptance Criteria

- [ ] The writeup covers: the rationale for the Python/C++ split and where the boundary was drawn (signal generation vs. risk/execution); the signal/order contract (Schema v1) as the seam, and why a versioned contract was chosen over a tightly coupled call interface; the multi-venue routing rationale (why crypto→Kraken, equity→IBKR by default); and at least the major known limitations/asymmetries (overlay backtest approximations from P1 Feature 3, IBKR vs Kraken fill-fidelity difference from P6, the deferred `venue_symbol` v2 schema question from P0).
- [ ] Every major design decision documented in the writeup traces back to a specific phase/feature in this spec series, so a reviewer can cross-reference "claim" to "implementation evidence" (Feature 2's compiled parity evidence, Feature 1's ablation results).
- [ ] The writeup is honest about what wasn't built or validated (e.g. IBKR live trading, futures/FX macro exposure, guaranteed Redis message delivery) rather than presenting the system as more complete than it is.

## Feature 4: Personal Live Trading Operating Procedure

**Description:** A practical runbook for the user's own ongoing use of the system for personal trading — startup/shutdown, monitoring, what to do when the circuit breaker or kill switch trips, how to interpret a reconciliation mismatch — distinct from the academic/capstone writeup.

### User Stories

- As the **system's operator**, I want a runbook I can follow at 11pm if something looks wrong, without needing to recall implementation details from memory.
- As the **system's operator**, I want a clear statement of what's actually live (Kraken) vs. paper (IBKR) at any given time, so I never confuse a paper P&L number with real account performance when making personal financial decisions.

### Acceptance Criteria

- [ ] The runbook documents: daily/routine startup (`make up`), how to check current trading mode per venue, how to interpret dashboard halt states (manual kill switch vs. drawdown breaker vs. reconciliation mismatch — each requiring a different response), and how to safely shut down/restart without losing portfolio state.
- [ ] The runbook explicitly and prominently states which venue is live (Kraken, post-P7) and which is paper-only (IBKR) at all times, with no ambiguity about which P&L figures represent real money.
- [ ] A documented procedure exists for the manual "acknowledge and resync" step from P7 Feature 2, written for the operator to follow without needing to read C++ source code.
- [ ] The runbook is tested by following it literally for at least one full real operational cycle (start, monitor, handle or simulate one halt condition, stop) before being considered final.

## Feature 5: Sellable-Product Packaging Assessment

**Description:** A deliberate, honest assessment of what would be required to move from "personal system" to either of the two commercial framings raised in the main spec's open questions (§9) — a research tool for other quants vs. a managed-execution offering — without committing to building either in this phase.

### User Stories

- As the **system's owner**, I want a clear-eyed gap analysis between "what exists today" and "what either commercial path would require," so I can make an informed decision about whether/how to pursue monetization, rather than assuming the personal system is already close to sellable as-is.

### Acceptance Criteria

- [ ] The assessment separately addresses the two framings from main spec §9: (a) backtest-engine-as-research-tool (what's needed: multi-tenancy, data licensing for any non-free price feeds, support/documentation burden) and (b) execution-stack-as-managed-strategy (what's needed: regulatory/compliance review, the explicit non-goal from main spec §1.2 around multi-tenant SaaS, custody/account-separation concerns).
- [ ] The assessment explicitly flags that this spec series and its implementation were not designed with regulatory compliance for a managed-strategy/advisory offering in mind, and that pursuing (b) would require legal review beyond the scope of any engineering spec.
- [ ] No code or infrastructure changes are made as part of this feature — it is a written assessment only, to inform a future, separate decision and (if pursued) a future, separate spec.
