# P0 — Schema v1 Definitions & Replay Export

**Phase goal:** Establish the canonical, versioned data contract that every later phase (Python research engine, C++ risk/execution engine, replay-based parity testing) builds against. No engine logic ships in P0 — only the contract, its validation rules, and the export mechanism that lets later phases exchange data deterministically.

---

## Feature 1: Signal Contract (Schema v1)

**Description:** A single, versioned definition of what a "trading signal" looks like as it crosses from the Python research/agent layer into the C++ risk/execution layer — covering regime, strategy, venue/asset routing, fused score, and the overlay/KG provenance fields introduced in the 7-agent architecture.

### User Stories

- As a **strategy developer**, I want every signal (from backtest or live agent) to carry the same fields in the same format, so I can swap between backtest replay and live signal streams without rewriting downstream consumers.
- As a **risk engineer**, I want the signal to explicitly state which venue and asset class it belongs to, so routing and risk-parameter selection (Section 6 of the main spec) can be done without inferring intent from the ticker name.
- As a **researcher running ablations**, I want news/macro/KG-formula contributions exposed as separate fields rather than baked into one opaque score, so I can zero out individual overlays and measure their effect.
- As a **capstone author**, I want a `graph_path` field on every signal that used KG grounding, so the audit trail for "why did the system trade this" is reconstructable from the data alone.

### Acceptance Criteria

- [ ] The contract defines exactly these fields, with documented type and valid range: `schema_version`, `cycle_id`, `timestamp`, `regime`, `strategy`, `ticker`, `venue`, `venue_symbol`, `asset_class`, `direction`, `score`, `quant_score`, `sentiment_score`, `news_overlay`, `macro_overlay`, `kg_formula_contribution`, `graph_path`, `contradiction_blocked`.
- [ ] `venue` is restricted to `kraken` | `ibkr`; `asset_class` to `equity_xstock` | `crypto` | `macro_proxy`; `direction` to `buy` | `sell` | `hold`.
- [ ] `score`, `quant_score`, `sentiment_score`, `news_overlay`, `macro_overlay`, `kg_formula_contribution` are all bounded to `[-1.0, 1.0]`.
- [ ] A signal where `asset_class = crypto` cannot declare `venue = ibkr` (and vice versa for equity/macro proxies routing to Kraken, per default routing rules in the main spec).
- [ ] A signal with `direction = hold` is internally consistent with the fusion threshold rule (i.e. `|score|` below the buy/sell threshold) — and the threshold itself is referenced from config, not hardcoded into the contract.
- [ ] `regime` values are validated against the actual `Regime` node names in `master.cypher` (not a separately-invented enum) — this is a P0 deliverable: produce the canonical list of 7 regime names from the KG and bake it into the schema.
- [ ] `graph_path` format (sequence of alternating Concept/Relationship names) matches what `SignalAgent`'s contradiction/formula traversal already produces — confirmed against current code, not redefined.
- [ ] `cycle_id` is a UUID shared across all signals emitted in one orchestrator cycle (enables grouping/joining downstream).
- [ ] `schema_version` is present and equals `1`; any consumer encountering a different value rejects the message rather than guessing field defaults.
- [ ] A written JSON Schema document for `Signal` exists and is the single source used to validate messages on both the Python and C++ sides (no parallel hand-maintained definitions).

## Feature 2: ApprovedOrder Contract (Schema v1)

**Description:** A single, versioned definition of what a "risk-approved order" looks like as it leaves the RiskEngine — whether produced live (C++) or in replay/parity testing (Python `risk_sim.py`).

### User Stories

- As a **risk engineer**, I want every approved order to carry the sizing rationale (`kelly_fraction`, `var_contribution_pct`, `risk_checks`), so an auditor can verify *why* a position was sized the way it was, not just what was sized.
- As an **execution developer**, I want `venue` and `mode` on every order, so the ExecutionEngine can route to the correct adapter (Kraken vs IBKR) and enforce paper-only IBKR without inspecting other fields.
- As a **compliance-minded operator**, I want it to be structurally impossible to construct an `ApprovedOrder` with `venue = ibkr` and `mode = live`, so an accidental live IBKR order can never reach the execution layer in this phase.
- As a **parity tester**, I want `ApprovedOrder` to retain a link (`cycle_id`) back to the originating `Signal`, so Python (`risk_sim.py`) and C++ (`RiskEngine`) outputs for the same input signal can be diffed directly.

### Acceptance Criteria

- [ ] The contract defines exactly these fields: `schema_version`, `order_id`, `cycle_id`, `ticker`, `venue`, `venue_symbol`, `direction`, `quantity`, `notional_usd`, `kelly_fraction`, `var_contribution_pct`, `mode`, `risk_checks` (with sub-fields `position_pct_ok`, `sector_pct_ok`, `var_ok`).
- [ ] `direction` is restricted to `buy` | `sell` — orders are never emitted for `hold`.
- [ ] `quantity` and `notional_usd` must be strictly positive.
- [ ] `kelly_fraction` is bounded to `[0, AGENT_KELLY_FRACTION]` (currently `[0, 0.5]`), reflecting the half-Kelly cap from the main spec's risk parameters.
- [ ] `var_contribution_pct` is bounded to `[0, 1]` and represents a fraction of NAV.
- [ ] `mode` is restricted to `paper` | `live`.
- [ ] **Hard rule**: any `ApprovedOrder` with `venue = ibkr` must have `mode = paper`. This rule is encoded in the schema itself (e.g. conditional schema constraint), not left to downstream code to check.
- [ ] An `ApprovedOrder` cannot be constructed/serialized if any of `risk_checks.*` is `false` — a failed risk check means "no order," not "an order flagged as failed."
- [ ] `cycle_id` on the order matches the `cycle_id` of the `Signal` that produced it, for traceability.
- [ ] A written JSON Schema document for `ApprovedOrder` exists, shared between Python and C++ validation.

## Feature 3: Schema Versioning Policy

**Description:** A documented, enforced policy for how `Signal` and `ApprovedOrder` evolve, so the Python↔C++ boundary doesn't silently drift as the system grows (e.g. the known future need to add IBKR exchange/currency fields).

### User Stories

- As a **maintainer**, I want any field addition or semantic change to require a `schema_version` bump, so I can reason about "what version of the contract is this message" without inspecting field-by-field.
- As a **C++ engine developer**, I want to declare the maximum schema version I support and reject anything higher, so an upstream Python change can't silently produce garbage sizing decisions in the risk engine.

### Acceptance Criteria

- [ ] Both `Signal` and `ApprovedOrder` carry `schema_version` as a required field; `1` is the only valid value for this phase.
- [ ] A short written policy exists stating: (a) additive, optional fields with safe defaults may still require a version bump if they affect risk/routing logic; (b) any change to an enum's valid values, a numeric range, or a required/optional status requires a version bump; (c) consumers must reject unsupported versions rather than attempt partial parsing.
- [ ] The known future change (IBKR `venue_symbol` needing exchange/currency decomposition — see Feature 1/2 dependencies) is documented as a flagged "v2 candidate" so it's planned rather than discovered mid-implementation.

## Feature 4: Signal Replay Export

**Description:** A mechanism for the Python research/backtest engine to emit a deterministic, ordered stream of `Signal` records to a file, which later phases (C++ `RiskEngine` parity testing, P7) will consume in a standalone replay mode.

### User Stories

- As a **backtest developer**, I want to export the exact sequence of signals my backtest generated, so I can later prove the C++ RiskEngine produces the same `ApprovedOrder`s as `risk_sim.py` for identical inputs (parity plan, main spec §7.2).
- As a **researcher**, I want each export run to carry metadata (date range, KG-grounded flag, universe, signal count), so a replay file is self-describing months later without needing the original run's logs.
- As a **reviewer**, I want exported signals to be in a deterministic order (by timestamp, then cycle, then strategy), so re-running the same backtest twice produces byte-identical export files — useful for regression diffing.

### Acceptance Criteria

- [ ] Exporting a backtest run produces one file containing one `Signal` (Schema v1) record per line, in a stable, deterministic order.
- [ ] A companion metadata record captures: run identifier, schema version, date range, `use_graph` flag, instrument universe, total signal count, and generation timestamp.
- [ ] Two exports of the same backtest configuration and code version produce identical output (byte-for-byte for the signal records).
- [ ] Every exported `Signal` independently passes the Feature 1 validation rules — the export step is not a place where invalid signals can sneak through.
- [ ] The export format and location convention is documented so the (future, P7) C++ replay runner knows what to consume without further negotiation.

## Out of Scope for P0

- Any RiskEngine, ExecutionEngine, or venue-adapter implementation (P3–P7).
- The actual C++ replay runner program (consumes the P0 export format, but is itself a P7 deliverable).
- Resolving the IBKR `venue_symbol` exchange/currency question — flagged as a v2 candidate (Feature 3), decision deferred to before P6.
- Backtest strategy logic, overlays, or metrics (P1/P2) — P0 only defines what a signal *is*, not how one is generated.

## Dependencies / Inputs Needed Before P0 Can Be Marked Done

1. Canonical list of the 7 `Regime` node names from `master.cypher` (Feature 1).
2. Confirmation of `graph_path` structure as currently produced by `SignalAgent` (Feature 1).
3. Confirmation of current `AGENT_KELLY_FRACTION` and fusion `score` threshold values from `.env`/`signal_agent.py`, so range constraints in Feature 1/2 reference real values rather than spec-author assumptions.
