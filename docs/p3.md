# P3 — C++ RiskEngine Core (Kelly/VaR/Position/Sector Caps + Circuit Breaker)

**Phase goal:** Implement the first C++ component of the production system — a standalone `RiskEngine` that takes a Schema v1 `Signal` and current portfolio state and produces a Schema v1 `ApprovedOrder` (or a structured rejection), reproducing `risk_sim.py` (P2) exactly. No Redis, no live data, no execution — P3 is purely "given the same inputs as `risk_sim.py`, does the C++ engine produce the same outputs." Depends on P0 (contracts) and P2 (`risk_sim.py` as ground truth).

---

## Feature 1: C++ Signal/Order Contract Implementation

**Description:** C++ representations of the Schema v1 `Signal` and `ApprovedOrder` (and their JSON serialization/validation), structurally and semantically identical to the Python dataclasses from P0 — so any message that's valid on one side is valid on the other.

### User Stories

- As a **C++ developer**, I want `Signal`/`ApprovedOrder` structs whose field names, types, and valid ranges are a direct mirror of the P0 Python contracts, so I'm not reinterpreting the schema from scratch.
- As a **parity tester**, I want the C++ JSON validation to reject the exact same malformed inputs that the Python `_validate_signal`/`_validate_order` functions reject (P0 Feature 1/2), so "invalid input" handling is consistent across both languages.
- As a **maintainer**, I want the C++ side to declare its supported `schema_version` explicitly and reject anything else, matching the P0 Feature 3 versioning policy.

### Acceptance Criteria

- [ ] C++ `Signal` and `ApprovedOrder` structs exist with fields matching P0's Python dataclasses exactly (names, types, enum value strings).
- [ ] JSON (de)serialization for both structs uses the JSON Schema documents produced in P0 Feature 1/2 as the validation source — not a separately hand-written set of checks that could drift from the Python side.
- [ ] The same validation rules enforced in P0 (range checks on scores/overlays, venue/asset_class consistency, IBKR-paper-only constraint, hold/score-threshold consistency, UUID format checks) are enforced in C++, producing rejections for the same inputs.
- [ ] `schema_version != 1` is rejected and logged with a clear "unsupported schema version" message, not silently parsed.
- [ ] A `risk_checks.all_passed() == false` `ApprovedOrder` cannot be constructed (mirrors P0 Feature 2's "no order for a failed check" rule).
- [ ] A small fixture set of valid and invalid JSON `Signal`/`ApprovedOrder` examples (shared between Python and C++ test suites) all produce matching accept/reject outcomes on both sides.

## Feature 2: Half-Kelly Position Sizing

**Description:** C++ implementation of the half-Kelly sizing logic from `risk_sim.py`, producing `kelly_fraction` and resulting `quantity`/`notional_usd` for a given `Signal` and portfolio state.

### User Stories

- As a **risk engineer**, I want the C++ engine's `kelly_fraction` output to match `risk_sim.py`'s output to within floating-point tolerance for the same inputs, so position sizes don't silently diverge between research and production.
- As a **maintainer**, I want `AGENT_KELLY_FRACTION` read from the same `.env` source (not hardcoded as `0.5` in C++), so a config change in one place affects both engines consistently.

### Acceptance Criteria

- [ ] `kelly_fraction` is computed using the same formula and inputs (`score`, win-rate/edge estimates, etc., per `risk_sim.py`'s extracted logic) as the Python reference.
- [ ] `kelly_fraction` is bounded to `[0, AGENT_KELLY_FRACTION]`, with the cap value read from `.env` at startup (not compiled in).
- [ ] For a fixed `(Signal, portfolio_state)` input, C++ `kelly_fraction`, `quantity`, and `notional_usd` match `risk_sim.py`'s output to within 1e-6 relative tolerance (per main spec §7.2 parity tolerance).
- [ ] A signal with `score = 0` (or below the buy/sell threshold) produces no order (not a zero-sized order) — consistent with P0's "orders are never emitted for hold" rule.

## Feature 3: Position & Sector Concentration Caps

**Description:** C++ implementation of `AGENT_MAX_POSITION_PCT` (per-instrument NAV cap) and `RISK_MAX_SECTOR_PCT` (per-sector NAV cap) checks, operating on a portfolio state structured to span multiple venues (per P2 Feature 3's forward-looking design).

### User Stories

- As a **risk engineer**, I want an order that would push a single instrument above `AGENT_MAX_POSITION_PCT` of NAV to be rejected (or sized down to the cap) identically in C++ and Python.
- As a **multi-venue operator (future)**, I want sector concentration computed across the *entire* portfolio regardless of which venue holds which position, so the cap can't be circumvented by spreading a sector bet across Kraken and IBKR.
- As a **crypto trader**, I want crypto positions excluded from sector-cap calculations (crypto = its own bucket, per main spec §6), matching `risk_sim.py`'s asset-class branching.

### Acceptance Criteria

- [ ] An order that would breach `AGENT_MAX_POSITION_PCT` is rejected with `position_pct_ok = false`, matching `risk_sim.py`'s rejection for the same input.
- [ ] An order that would breach `RISK_MAX_SECTOR_PCT` for instruments with `asset_class` ∈ {`equity_xstock`, `macro_proxy`} is rejected with `sector_pct_ok = false`; crypto instruments are never sector-capped.
- [ ] Portfolio state input accepts positions tagged by `venue`, and sector/position calculations aggregate across all venues present in the input — even though P3's test harness only ever supplies single-venue or synthetic multi-venue fixtures (no live IBKR/Kraken connectivity yet).
- [ ] For the same `(Signal, portfolio_state)` fixture, position-cap and sector-cap pass/fail outcomes match `risk_sim.py` exactly across a fixture set covering: under-cap, at-cap, over-cap, and crypto-instrument-ignores-sector-cap cases.

## Feature 4: Parametric VaR Check

**Description:** C++ implementation of the `RISK_VAR_CONFIDENCE`-based parametric VaR contribution check, rejecting orders whose `var_contribution_pct` would exceed `RISK_MAX_VAR_PCT`.

### User Stories

- As a **risk engineer**, I want VaR contribution computed using the exact same parametric methodology (lookback window, distributional assumption) confirmed in P2, so a position that's "VaR-acceptable" in backtest is also acceptable in production.
- As a **maintainer**, I want `RISK_VAR_CONFIDENCE` and `RISK_MAX_VAR_PCT` read from `.env`, with no separate copies hardcoded in C++.

### Acceptance Criteria

- [ ] `var_contribution_pct` is computed using the same parametric VaR methodology (confirmed in P2 Dependency 3) at `RISK_VAR_CONFIDENCE` (99% by default).
- [ ] An order whose `var_contribution_pct` would exceed `RISK_MAX_VAR_PCT` is rejected with `var_ok = false`.
- [ ] For a fixture set spanning under-limit, at-limit, and over-limit VaR contributions, C++ pass/fail outcomes and `var_contribution_pct` values (to 1e-6 tolerance) match `risk_sim.py`.
- [ ] Both `RISK_VAR_CONFIDENCE` and `RISK_MAX_VAR_PCT` are configurable via `.env` and changing them produces matching behavior changes in both engines.

## Feature 5: Drawdown Circuit Breaker

**Description:** C++ implementation of the `AGENT_MAX_DRAWDOWN_HALT` circuit breaker — once portfolio drawdown-from-peak exceeds the threshold, all signals are rejected (halted) until drawdown recovers, matching `risk_sim.py`'s P2 Feature 3/4 behavior.

### User Stories

- As a **risk engineer**, I want the circuit breaker to halt *all* order approval the instant drawdown crosses the threshold, regardless of which `Signal` triggered the breach — so no "one more trade slips through" edge case exists.
- As an **operator**, I want the halted state to be queryable from the `RiskEngine` itself (not just inferred from "no orders for a while"), so later phases (P5) can propagate it to `/agent/status` reliably.

### Acceptance Criteria

- [ ] When portfolio drawdown-from-peak (computed from portfolio state input) exceeds `AGENT_MAX_DRAWDOWN_HALT`, every subsequent `Signal` is rejected with a "halted" reason until drawdown recovers below the threshold.
- [ ] The halted/not-halted state is exposed as an explicit, queryable property of the `RiskEngine` instance (not derived externally from rejection patterns).
- [ ] A fixture sequence that crosses the drawdown threshold, stays halted for several signals, then recovers, produces identical accept/reject/halted-state transitions in C++ and `risk_sim.py`.
- [ ] `AGENT_MAX_DRAWDOWN_HALT` is read from `.env`; setting it to an unreachable value (e.g. 100%) produces behavior identical to having no circuit breaker, matching P2 Feature 4's equivalent acceptance criterion.

## Feature 6: Unit Parity Test Suite

**Description:** A C++ test suite (`tests/test_risk_engine.cpp`) that ports every relevant case from `make test-agents` / `risk_agent.py`'s existing test cases, plus the fixture sets defined in Features 2–5, asserting C++ output matches `risk_sim.py` output within tolerance.

### User Stories

- As a **maintainer**, I want a single test command that proves "C++ RiskEngine agrees with Python risk_sim.py" across every known test case, so future changes to either side that break parity are caught immediately.
- As a **capstone author**, I want this parity suite's pass status to be part of the system's documented validation evidence (main spec §7.1), so the "dual-engine" architecture claim is backed by tests, not assertion.

### Acceptance Criteria

- [ ] Every test case in `risk_agent.py`'s existing test suite (`make test-agents` Layer 4) has a corresponding C++ test with the same inputs and expected outputs.
- [ ] All fixture sets from Features 1–5 (valid/invalid contracts, Kelly sizing, position/sector caps, VaR, circuit breaker) are included as C++ test cases.
- [ ] The full C++ test suite runs via a single command (e.g. `ctest` or equivalent) and passes with the C++ `RiskEngine` matching `risk_sim.py` outputs to within the documented 1e-6 tolerance.
- [ ] Test fixtures (input JSON for `Signal`/portfolio state, expected `ApprovedOrder`/rejection) are stored in a format usable by *both* the Python and C++ test suites — single source of fixture data, not duplicated/hand-copied between languages.
- [ ] CI (or documented manual procedure, if CI isn't yet set up) runs this parity suite on every change to `risk_sim.py` or the C++ `RiskEngine`.

## Out of Scope for P3

- `ExecutionEngine`, venue adapters (Kraken/IBKR), Postgres audit logging — P4.
- Redis pub/sub integration — P5.
- Any live or paper order submission — `RiskEngine` in P3 only produces `ApprovedOrder` objects in-memory/to test output; it does not send anything anywhere.
- The standalone `replay_runner` CLI tool that consumes P0 Feature 4's export files — P7, though P3's `RiskEngine` is the component `replay_runner` will wrap.

## Dependencies / Inputs Needed Before P3 Can Be Marked Done

1. P2 complete: `risk_sim.py` finalized and treated as frozen ground truth — any subsequent change to `risk_sim.py` after P3 starts must be re-validated against C++ (flag this as a process risk if P2 and P3 timelines overlap).
2. CMake/C++20 toolchain and chosen JSON/testing libraries (`nlohmann/json`, `Catch2`/`GoogleTest`) available in the local Docker build environment — confirm before Feature 1 implementation.
3. Shared fixture format (Feature 6) agreed upon — e.g. JSON files under a common `tests/fixtures/` directory referenced by both `pytest` and `ctest`.
