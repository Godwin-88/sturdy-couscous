# P5 — Redis Integration: Orchestrator → RiskEngine Live Wiring

**Phase goal:** Replace the file-based signal stream from P4 with live Redis pub/sub — the Python `agent-worker` (RegimeAgent → NewsAgent → MacroCalendarAgent → KGSignalGenerator → SignalAgent, post-overlay, post-fusion, post-contradiction-check) publishes Schema v1 `Signal` objects to Redis; the C++ `risk-engine` service (P3+P4) subscribes, processes, and the existing dashboard reflects it all — with zero frontend changes. This is the phase where the dual-engine architecture goes from "two things that work separately" to "one live system." Depends on P3 (RiskEngine), P4 (ExecutionEngine/audit/events), and requires `agent-worker` refactoring.

---

## Feature 1: `agent-worker` Refactor — Signal Emission

**Description:** Refactor the Python orchestrator so that, after the existing signal-merge sequence (regime → news overlay → macro overlay → KG formula → fusion → contradiction check), it **publishes** Schema v1 `Signal` objects to Redis instead of calling `RiskAgent`/`ExecutionAgent` in-process.

### User Stories

- As a **maintainer**, I want this refactor to be a "publish instead of call" change only — the signal-merge logic itself (regime determination, overlays, fusion, contradiction checks) is untouched, so the existing ablation/backtest validation (P1/P2) remains valid for this part of the pipeline.
- As a **risk engineer**, I want every signal `agent-worker` currently feeds to `RiskAgent` to instead be published as a Schema v1 `Signal`, with no signals silently dropped or transformed differently than before.
- As a **parity tester**, I want the published `Signal` stream to be inspectable/loggable independent of the C++ engine, so I can verify "what Python decided to publish" separately from "what C++ decided to do with it."

### Acceptance Criteria

- [ ] After the contradiction-check step, `agent-worker` constructs a Schema v1 `Signal` object (per P0 Feature 1) for each strategy/ticker combination that previously would have been passed to `RiskAgent`.
- [ ] Each `Signal` is validated (P0 Feature 1 rules) before publishing; a `Signal` that fails validation is logged as an error and **not** published (rather than crashing the cycle or publishing invalid data).
- [ ] `RiskAgent` and `ExecutionAgent` are no longer called in-process by `agent-worker` — their logic now lives exclusively in the C++ `risk-engine` (P3/P4).
- [ ] The orchestrator's pre-publish pipeline (regime → overlays → fusion → contradiction check) produces identical `score`/`quant_score`/`sentiment_score`/`news_overlay`/`macro_overlay`/`kg_formula_contribution`/`contradiction_blocked` values before and after this refactor, for the same market inputs — verified by re-running the P1/P2 ablation suite and confirming unchanged results (per main spec §7.4 ablation regression).
- [ ] Every signal in one orchestrator cycle shares the same `cycle_id` (UUID), generated once per cycle.
- [ ] A configuration flag or environment toggle allows reverting to the pre-refactor in-process behavior during transition/testing (a "shadow mode" — publish to Redis *and* still call the old Python `RiskAgent` path, comparing outputs) — see Feature 4.

## Feature 2: Redis Channel Definition & Publishing

**Description:** Define and implement the `graphalpha:signals:v1` Redis pub/sub channel (or confirm reuse of an existing channel) that carries Schema v1 `Signal` JSON from `agent-worker` to `risk-engine`.

### User Stories

- As a **maintainer**, I want the channel name and message format versioned (`:v1` suffix or equivalent), so a future Schema v2 can run alongside v1 during a migration rather than requiring a synchronized cutover.
- As an **operator**, I want to be able to inspect the live signal stream (e.g. via `redis-cli SUBSCRIBE`) for debugging, without needing the C++ engine running.

### Acceptance Criteria

- [ ] A Redis channel (e.g. `graphalpha:signals:v1`) is defined, with the version suffix matching `Signal.schema_version` — any future schema bump uses a new channel name, not a silent format change on the same channel.
- [ ] `agent-worker` publishes each validated `Signal` (Feature 1) as a JSON message on this channel immediately after construction — no batching/delaying that would desynchronize `cycle_id` groupings.
- [ ] An operator can subscribe to this channel independently (e.g. `redis-cli SUBSCRIBE graphalpha:signals:v1`) and see human-readable Schema v1 JSON for every signal published during a live cycle.
- [ ] Channel choice and message framing are documented in a short README/runbook addition, including how to distinguish "no signals this cycle" (legitimate — e.g. all holds) from "agent-worker not publishing" (a fault condition).

## Feature 3: `risk-engine` Subscription & Cycle Processing

**Description:** Extend the P4 standalone binary so it subscribes to the Feature 2 Redis channel (replacing the file-based input), processes each incoming `Signal` through `RiskEngine` → `ExecutionEngine` as it arrives, and continues writing audit rows and publishing `/ws/events`.

### User Stories

- As an **operator**, I want `risk-engine` to process signals as they arrive in real time, with the same per-signal pipeline P4 validated against a file — so going live is "swap the input source," not "rebuild the pipeline."
- As a **maintainer**, I want `risk-engine` to handle a Redis disconnection gracefully (reconnect/backoff), so a transient Redis restart doesn't require manually restarting `risk-engine`.
- As a **risk engineer**, I want `risk-engine` to reject and log (not crash on) any message on this channel that fails Schema v1 validation or carries an unsupported `schema_version` — per P0 Feature 3's versioning policy.

### Acceptance Criteria

- [ ] `risk-engine` subscribes to `graphalpha:signals:v1` on startup and processes each received `Signal` through the same `RiskEngine` → `ExecutionEngine` pipeline validated in P3/P4, with no behavioral difference from the file-based P4 flow for equivalent input.
- [ ] A received message that fails JSON Schema validation, or whose `schema_version` is unsupported, is logged with the raw message content and **does not** crash or restart the service.
- [ ] On Redis disconnection, `risk-engine` attempts reconnection with backoff and resumes processing without manual intervention; no signals published during a disconnection are silently expected to be replayed (this is a known gap — Feature 5 addresses it).
- [ ] `risk-engine`'s portfolio state (P4 Feature 2) continues to be correctly updated and persisted as live signals are processed, exactly as validated with file input in P4.
- [ ] Processing latency per signal (Redis receive → `ApprovedOrder`/rejection → audit write → event publish) is measured and logged, establishing a baseline for the "sub-100ms decision latency" target from the main spec §1.2.

## Feature 4: Shadow Mode — Parallel-Run Validation

**Description:** A transition mechanism allowing the new Redis→C++ pipeline to run **alongside** the existing in-process Python `RiskAgent`/`ExecutionAgent` path for a validation period, comparing outputs before fully cutting over.

### User Stories

- As an **operator running real paper money**, I want to verify the new C++ pipeline makes the same sizing/rejection decisions as the existing Python path *before* the Python path is removed, so cutover doesn't introduce a silent regression in live trading.
- As a **maintainer**, I want shadow-mode discrepancies logged in a structured, reviewable way, so "C++ said X, Python said Y for the same signal" is a debuggable artifact, not a vague suspicion.

### Acceptance Criteria

- [ ] During shadow mode, `agent-worker` both (a) publishes Schema v1 `Signal`s to Redis (Feature 1/2) and (b) continues calling the existing Python `RiskAgent`/`ExecutionAgent` path as it does pre-refactor — `risk-engine` processes (a) but does **not** submit real orders (paper fills only, as in P4) while (b) remains the system of record.
- [ ] For each `cycle_id`, the `ApprovedOrder`/rejection produced by `risk-engine` (C++) and the equivalent decision produced by the existing Python path are logged side-by-side (e.g. to a `shadow_comparison` table or log file).
- [ ] Discrepancies (different `kelly_fraction`, different accept/reject outcome, different `quantity`/`notional_usd` beyond 1e-6 tolerance) are flagged distinctly from agreements, with enough context (`cycle_id`, `Signal`, both decisions) to debug without re-running anything.
- [ ] A documented exit criterion exists for shadow mode (e.g. "N consecutive cycles with zero discrepancies") before Feature 1's "remove old Python `RiskAgent`/`ExecutionAgent` calls" step is considered complete/permanent.
- [ ] Shadow mode can be toggled via `.env`/config without code changes, so it can be re-enabled after any future change to either `risk_sim.py` or the C++ `RiskEngine` as a quick regression check.

## Feature 5: Docker Compose Integration

**Description:** Add `risk-engine` as a service in `docker-compose.yml` alongside the existing `agent-worker`, `memgraph`, `postgres`, `redis`, `api`, `frontend` — completing the local-Docker-first deployment model from main spec §10.

### User Stories

- As an **operator**, I want `make up` to start `risk-engine` alongside everything else, with correct startup ordering (Redis/Postgres available before `risk-engine` connects), so there's no manual multi-step startup procedure.
- As a **maintainer**, I want `risk-engine`'s logs visible via the same `docker compose logs` workflow as other services, so debugging a live issue doesn't require a different toolchain.

### Acceptance Criteria

- [ ] `docker-compose.yml` includes a `risk-engine` service built from the P4 multi-stage Dockerfile, with `depends_on` ordering ensuring `redis` and `postgres` are healthy before `risk-engine` starts.
- [ ] `risk-engine` reads the same `.env` file as other services (Section 5.5 of main spec) — no separate env file.
- [ ] `make up` brings up a fully working system: `agent-worker` publishing signals, `risk-engine` consuming and producing audit/events, dashboard reflecting live activity — verified as a smoke test.
- [ ] `docker compose logs risk-engine` shows structured, readable logs for signal receipt, risk decisions, fills, and any rejections/errors.
- [ ] If `risk-engine` is stopped (e.g. for a rebuild) while `agent-worker` continues publishing, `agent-worker` does not crash or block — published signals during the outage are simply not processed (acknowledged gap, consistent with Feature 3's Redis-disconnection note; not a delivery-guarantee system in this phase).

## Out of Scope for P5

- IBKR / IB Gateway integration — P6.
- Kraken **live** order submission (vs. the paper simulation already validated in P4) — P7. P5's `risk-engine` continues operating in paper mode end-to-end.
- Guaranteed message delivery / replay-on-reconnect for the Redis channel (Feature 3's disconnection gap) — flagged as a known limitation, not solved in this phase. If this becomes a real operational problem during shadow mode, it should be raised as a candidate for a P5.5 addendum rather than silently deferred indefinitely.
- Removing `RiskAgent`/`ExecutionAgent` Python code entirely — Feature 4's shadow mode keeps it running until its exit criterion is met; actual code removal can happen at the end of P5 or be deferred to a cleanup task after P7.

## Dependencies / Inputs Needed Before P5 Can Be Marked Done

1. P3 and P4 complete and individually validated (parity suite passing, file-based end-to-end test passing).
2. Confirmation of `agent-worker`'s current cycle structure — specifically, where in the existing code the "call RiskAgent" step occurs, so Feature 1's refactor is a precise, minimal-diff change.
3. A decision on Feature 4's shadow-mode exit criterion (e.g. number of cycles, tolerance for discrepancies) — should be agreed before shadow mode begins, not improvised mid-run.
4. Confirmation of current Redis connection configuration (host/port/auth) used by `agent-worker`, so `risk-engine` connects to the same instance without new infrastructure.
