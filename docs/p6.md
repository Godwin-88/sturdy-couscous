# P6 — Interactive Brokers Integration (Paper Trading)

**Phase goal:** Add Interactive Brokers as the system's second execution venue, paper-only, for equity/ETF and macro-proxy instruments — while crypto stays on Kraken. This means standing up IB Gateway as a Docker service, building the C++ `IBKRAdapter`, extending `ExecutionEngine` to route by venue, and validating that cross-venue NAV/risk aggregation (designed for, but unused, since P3) actually works with two real position sources. Depends on P3 (RiskEngine), P4 (ExecutionEngine/audit/events), P5 (live Redis wiring) — this phase activates the cross-venue capability those phases were built to support.

---

## Feature 1: IB Gateway Docker Service

**Description:** A headless IB Gateway instance running as a Docker Compose service, authenticated against an IBKR **paper trading** account, reachable by `risk-engine` over the Compose network.

### User Stories

- As an **operator**, I want IB Gateway to start via `make up` like every other service, with no manual desktop-app login step, so the Docker-first deployment model (main spec §10) holds for IBKR too.
- As an **operator**, I want the Gateway to survive its ~24h session timeout without my intervention, so an overnight or weekend paper-trading run doesn't silently go dark.
- As a **security-conscious operator**, I want IBKR credentials sourced from `.env` (not baked into an image or committed anywhere), consistent with how Kraken API keys are already handled.

### Acceptance Criteria

- [x] `docker-compose.yml` includes an `ib-gateway` service (e.g. a community headless image bundling IBC for auto-login) configured via `.env` (`IBKR_USERNAME`, `IBKR_PASSWORD`, `IBKR_TRADING_MODE=paper`).
- [x] The Gateway connects to IBKR's **paper trading** environment specifically — confirmed by checking the account/session info exposed by the Gateway after startup, not assumed from config alone.
- [x] `risk-engine` can reach the Gateway at `ib-gateway:4002` (or whatever port the paper Gateway exposes) purely over the internal Compose network — no host networking or port forwarding required for normal operation.
- [ ] The Gateway auto-recovers from its periodic session timeout without manual restart, verified by leaving it running across at least one full timeout cycle.
- [ ] `docker compose logs ib-gateway` surfaces login success/failure and session-renewal events in readable form, so authentication problems are diagnosable from logs alone.
- [ ] If IBKR credentials are missing/invalid, the Gateway fails to authenticate loudly (visible in logs, and ideally surfaced to `/agent/status`) rather than silently running in a half-connected state that `risk-engine` can't distinguish from "working."

## Feature 2: C++ `IBKRAdapter`

**Description:** A C++ client implementing the venue-adapter interface (parallel to the existing `KrakenAdapter`) that connects to IB Gateway over its socket API, submits paper orders, and reports fills back to `ExecutionEngine`.

### User Stories

- As an **execution developer**, I want `IBKRAdapter` to expose the same interface `ExecutionEngine` already uses for `KrakenAdapter`, so routing logic (Feature 3) doesn't need venue-specific branching outside the adapter itself.
- As a **risk-aware operator**, I want it to be structurally impossible for `IBKRAdapter` to submit a live order, regardless of what `mode` value somehow reaches it, so a config mistake can't accidentally risk real capital on a venue this phase explicitly scopes as paper-only.
- As a **capstone author**, I want IBKR fills to come from the Gateway's own simulated fill engine (not GraphAlpha's internal slippage formula), so the documented fidelity difference from main spec §5.6 is real, not aspirational.

### Acceptance Criteria

- [x] `IBKRAdapter` implements the same adapter interface as `KrakenAdapter` (submit order, receive fill/rejection, report current positions) — `ExecutionEngine` interacts with both through one abstraction.
- [x] `IBKRAdapter` connects to IB Gateway via the official TWS API C++ client (or equivalent socket client), using contract specifications (`symbol`/`exchange`/`currency`) derived from the `Signal`/`ApprovedOrder`'s `venue_symbol`.
- [x] **Hard rule, enforced in code, not just convention**: `IBKRAdapter` rejects and refuses to submit any order where `mode != "paper"` — this check exists independently of (in addition to) the P0/P3 schema-level constraint, as defense in depth.
- [x] Submitted orders use IBKR's paper-account order submission; the reported fill price/timestamp comes from the Gateway's response, not computed locally.
- [x] If the resolved `venue_symbol` doesn't decompose cleanly into a valid IBKR contract (per the P0 Feature 3 "v2 candidate" flag on exchange/currency decomposition), the order is rejected with a clear error rather than submitted with a guessed/default exchange or currency.
- [x] Connection loss to IB Gateway is detected and handled — in-flight orders' status is reconciled on reconnect (queried from the Gateway) rather than assumed lost or assumed filled.

## Feature 3: Venue-Routed `ExecutionEngine`

**Description:** Extend `ExecutionEngine` (originally Kraken-only from P4) to route each `ApprovedOrder` to the correct adapter based on its `venue` field, with both adapters' fill results flowing into the same audit/event/portfolio-state pipeline.

### User Stories

- As a **maintainer**, I want adding IBKR to be additive to `ExecutionEngine` — the Kraken path (P4) continues working unmodified, and routing is a single dispatch point based on `venue`.
- As an **operator**, I want a fill from either venue to appear identically in the dashboard (same event format, same audit table), so I don't need venue-specific dashboard knowledge to monitor the system.

### Acceptance Criteria

- [x] `ExecutionEngine` dispatches each `ApprovedOrder` to `KrakenAdapter` or `IBKRAdapter` based solely on `order.venue`, with no other field inspected for routing purposes.
- [x] Fill results from both adapters are normalized into the same internal fill-result structure (P4 Feature 1's shape) before being passed to audit logging (P4 Feature 3) and event publishing (P4 Feature 4).
- [x] `order_audit` rows and `/ws/events` messages are tagged with `venue` so an operator can filter/distinguish Kraken vs IBKR activity in the existing dashboard without any frontend code change (the field is already present in the schema; this confirms it's populated correctly end-to-end for IBKR).
- [ ] Re-running the P4 file-based end-to-end test (Kraken-only fixtures) produces identical results post-refactor, confirming the routing change didn't alter Kraken behavior.
- [x] A new fixture-based test exercises IBKR-routed orders through the same `ExecutionEngine` entry point, confirming the dispatch and normalization work correctly for the new venue.

## Feature 4: Cross-Venue Portfolio State & Risk Aggregation

**Description:** Activate the cross-venue portfolio aggregation that `RiskEngine` (P3) and portfolio state tracking (P4) were structurally designed for since P3 — now with real positions from two venues feeding sector caps, VaR, NAV, and the drawdown circuit breaker.

### User Stories

- As a **risk engineer**, I want a sector concentration bet that's split across an IBKR equity position and a... (n/a for crypto, since crypto isn't sector-capped) — more precisely: I want two *different equity* positions on IBKR plus any equity-like Kraken xStock exposure to be correctly summed against `RISK_MAX_SECTOR_PCT`, so the cap can't be bypassed by venue choice.
- As an **operator**, I want the drawdown circuit breaker to trip based on **combined** NAV across both venues, so a loss concentrated on one venue still halts trading system-wide.
- As a **parity tester**, I want this to be the first real test of the "portfolio state spans multiple venues" design from P3 Feature 3 — confirming that design decision was sound, not just theoretically future-proof.

### Acceptance Criteria

- [x] Portfolio state (P4 Feature 2) now aggregates real positions from both `KrakenAdapter` and `IBKRAdapter`, with NAV computed as the sum across both venues.
- [x] Sector concentration checks (P3 Feature 3) correctly sum exposure for instruments sharing a sector regardless of which venue holds them.
- [x] The drawdown circuit breaker (P3 Feature 5) triggers based on combined cross-venue NAV drawdown-from-peak — a fixture test confirms a drawdown caused entirely by IBKR positions (with Kraken flat) still halts new orders **on both venues**.
- [x] Position-level caps (`AGENT_MAX_POSITION_PCT`) remain per-instrument and are evaluated correctly whether the instrument lives on Kraken or IBKR.
- [x] Service restart correctly reconstructs cross-venue state from Postgres (extending P4 Feature 2's restart behavior to cover both venues' positions).

## Feature 5: Orchestrator Venue Assignment Confirmation

**Description:** Confirm and validate that signals published by `agent-worker` (P5) carry the correct `venue` for IBKR-eligible instruments — this is largely a verification feature, since `Signal.venue` was already part of the P0 contract and P1's `universe.py`, but P6 is the first time it's exercised against a real second venue.

### User Stories

- As a **maintainer**, I want confirmation that the existing `venue` assignment logic (default: crypto → Kraken, equity/macro-proxy → IBKR) actually produces correctly-routed live signals now that there's a real venue on the other end to expose a misrouting.
- As an **operator**, I want to override the default venue assignment per ticker (e.g. trade an equity xStock on Kraken instead of IBKR) without code changes, since main spec §4.3 allows this as a valid configuration choice.

### Acceptance Criteria

- [x] For every instrument in `KG_SIGNAL_TICKERS`, live published signals carry the `venue` matching `universe.py`'s assignment (crypto → kraken; equity/macro-proxy → ibkr by default).
- [ ] An operator can override a specific ticker's venue assignment via configuration (not code), and the change is reflected in the next published `Signal` for that ticker without restarting unrelated services.
- [ ] A live signal for an IBKR-routed ticker, traced end-to-end (published → `RiskEngine` → `IBKRAdapter` → fill → audit row → dashboard event), is confirmed to actually reach IB Gateway and produce a real paper fill — not just pass validation and stop short of execution.

## Out of Scope for P6

- Any live (non-paper) IBKR order — explicitly out of scope per main spec §1.2/§5.6; `IBKRAdapter` (Feature 2) enforces this in code, not just by configuration default.
- Resolving the `venue_symbol` exchange/currency decomposition as a full schema v2 — P6 must work *within* the current v1 constraint (Feature 2's "reject if it doesn't decompose cleanly" rule), with the v2 decision still deferred per P0 Feature 3, though P6 is likely to surface concrete evidence for *why* v2 is needed.
- IBKR market data subscriptions for the backtest engine (P1) — P1's data loaders remain yfinance/Kraken-only; P6 only adds IBKR for execution, not as a price-data source.
- Direct futures/FX macro exposure via IBKR (main spec §9 open question) — P6 covers equity/ETF and the existing TLT-style macro proxy only.
