# P1 — Python Multi-Asset Event-Driven Backtest Engine

**Phase goal:** Stand up the research-side backtesting engine that reproduces the live orchestrator's full signal-merge sequence (regime → news overlay → macro overlay → KG formula signals → quant+sentiment fusion → contradiction check) across the multi-venue, multi-asset universe (equities/xStocks, crypto, macro proxies), emitting Schema v1 `Signal` records that Feature 4 of P0 can export. Depends on P0 being complete (contract frozen, regime names confirmed, `graph_path` format confirmed).

---

## Feature 1: Multi-Asset Universe Definition

**Description:** A single configuration source describing every instrument the backtest engine can trade — its ticker, asset class, venue, venue-native symbol, and sector — so strategies, overlays, and the risk simulator all branch off the same source of truth rather than inferring properties from ticker names.

### User Stories

- As a **backtest developer**, I want one place that says "BTC-USD is crypto, routes to Kraken, has no sector," so I never have to special-case instrument properties inside strategy code.
- As a **researcher**, I want the universe to match `KG_SIGNAL_TICKERS` (SPY, QQQ, TLT, GLD, BTC-USD) by default, so backtest results are directly comparable to what KGSignalGenerator evaluates live.
- As a **risk-parity tester**, I want each instrument's `venue` assignment to follow the documented default routing rules (crypto → Kraken, equity/macro proxy → IBKR), so `Signal.venue` validation (P0 Feature 1) never fails on a routing mismatch during backtest.

### Acceptance Criteria

- [ ] Universe configuration exists for, at minimum, the `KG_SIGNAL_TICKERS` set (SPY, QQQ, TLT, GLD, BTC-USD), each tagged with `asset_class`, `venue`, `venue_symbol`, and (where applicable) `sector`.
- [ ] Crypto instruments are assigned `venue = kraken`; equity/macro-proxy instruments are assigned `venue = ibkr` by default, consistent with main spec §4.3/§5.6 routing rules.
- [ ] The universe is extensible — adding a new ticker requires only a new entry in this configuration, with no code changes elsewhere in the backtest engine.
- [ ] Every universe entry, when used to populate a `Signal`, produces a venue/asset_class combination that passes P0 Feature 1 validation (no instrument is defined in a way that's structurally invalid).
- [ ] Sector tags use a consistent taxonomy (e.g. GICS) sufficient for the sector concentration check in P2/P3.

## Feature 2: Multi-Asset Historical Data Loading

**Description:** Loaders that retrieve historical OHLCV data for every instrument in the universe, from the appropriate source per asset class (yfinance for equities/macro proxies, Kraken public API for crypto), with consistent output format regardless of source.

### User Stories

- As a **backtest developer**, I want equities, macro proxies, and crypto to come back from `loaders.py` in the same shape (OHLCV + timestamp, indexed consistently), so the event loop doesn't need per-asset-class branching just to read prices.
- As a **researcher**, I want corporate actions (splits/dividends) applied to equity data before backtest, so strategy signals aren't distorted by unadjusted price jumps.
- As an **operator**, I want a clear, loud failure if historical data for a universe instrument is unavailable for the requested date range, rather than a silently shortened or interpolated series.

### Acceptance Criteria

- [ ] For every instrument in the Feature 1 universe, historical OHLCV can be loaded for an arbitrary `[start, end]` date range.
- [ ] Equity/macro-proxy data is split/dividend-adjusted before being returned to the engine.
- [ ] Crypto data granularity (hourly/daily) is configurable per run, with daily as the default to match the equity cadence used elsewhere in the system.
- [ ] All loaders return data in one common schema (e.g. same column names, same timezone convention — UTC), regardless of source.
- [ ] If data for any universe instrument is missing/incomplete for the requested range, the loader raises a clear error identifying the instrument and the gap, rather than proceeding with partial data.

## Feature 3: Overlay Modules (News & Macro)

**Description:** Backtest-time approximations of `NewsAgent` and `MacroCalendarAgent`, producing the `news_overlay` and `macro_overlay` values that feed into `Signal` per the v0.3 contract — with each overlay independently toggleable for ablation.

### User Stories

- As a **researcher**, I want to run a backtest with `news_overlay` and `macro_overlay` both zeroed out, and separately with each enabled, so I can isolate each agent's contribution to performance (Differentiator #6).
- As a **capstone author**, I want the overlay approximation method (historical corpus replay vs. neutral pass-through) to be explicit and documented per overlay, so the validity/limitations of the ablation results are clear in the writeup.
- As a **backtest developer**, I want overlay values to be produced in the same `[-1.0, 1.0]` range and applied at the same point in the fusion sequence as the live `SignalAgent`, so backtest and live scores are comparable.

### Acceptance Criteria

- [ ] `news_overlay` and `macro_overlay` are each computed per `(ticker, timestamp)` and fall within `[-1.0, 1.0]`, matching P0 Feature 1 bounds.
- [ ] Each overlay module documents which approximation it uses (e.g. "macro_overlay uses FRED economic calendar pre-event dampening windows replayed historically"; "news_overlay uses neutral pass-through (0.0) — historical RSS corpus not available in this phase").
- [ ] CLI flags `--disable-news-overlay` and `--disable-macro-overlay` independently force the corresponding overlay to `0.0` for the entire run, without altering any other part of the signal pipeline.
- [ ] The point in the fusion sequence where overlays are applied (after the 70/30 quant/sentiment fusion, before the final `score`) matches the live orchestrator's order of operations exactly.
- [ ] Running the same backtest with overlays enabled vs. disabled produces different `score` values only — `quant_score`, `sentiment_score`, and `kg_formula_contribution` are unaffected, confirming overlay independence.

## Feature 4: KG Formula Signal Generation (Backtest Mode)

**Description:** A backtest-mode `KGSignalGenerator` that evaluates Formula nodes from the KG against historical price data, producing `kg_formula_contribution` values consistent with what the live agent would produce on the same data.

### User Stories

- As a **researcher**, I want KG Formula nodes evaluated against historical prices exactly as they would be evaluated live, so backtest performance attributable to KG-grounded formulas is a fair estimate of live performance.
- As a **strategy developer**, I want formula evaluation to fail loudly (not silently return 0.0) if a Formula node references a concept/ticker not present in the backtest universe, so gaps in KG-to-universe coverage are caught during development, not discovered as silent zeros in results.

### Acceptance Criteria

- [ ] For each ticker in the universe with one or more applicable KG Formula nodes, `kg_formula_contribution` is computed at each backtest timestep using the same formula definitions queried live (read from the same Memgraph instance/KG export used elsewhere in the system).
- [ ] `kg_formula_contribution` falls within `[-1.0, 1.0]` per P0 Feature 1 bounds.
- [ ] If a Formula node references data not available in the backtest's loaded universe (Feature 2), the engine raises an explicit error identifying the missing reference rather than defaulting to `0.0`.
- [ ] For a fixed historical date and fixed KG state, repeated runs produce identical `kg_formula_contribution` values (deterministic evaluation).

## Feature 5: Strategy Library (Grounded & Ungrounded)

**Description:** The set of backtestable strategies needed to support the existing three-mode comparison (KG-grounded, ungrounded baseline, ablation) across the expanded multi-asset universe — momentum, GARCH-vol, Bayesian-network proxy, value, and crisis strategies.

### User Stories

- As a **researcher**, I want an ungrounded `MomentumOverlay` baseline that runs regardless of regime/graph state, so the ablation comparison (grounded vs ungrounded) has a stable reference point.
- As a **strategy developer**, I want each strategy to implement one common interface (`generate_signal(bar, kg_context) -> Signal`), so adding a new strategy doesn't require touching the event loop.
- As a **risk-parity tester**, I want every strategy-produced `Signal` to already be a valid Schema v1 object before it reaches overlays/fusion, so validation failures are attributable to the strategy, not the pipeline.

### Acceptance Criteria

- [ ] At minimum, momentum, GARCH-vol, Bayesian-network proxy, value, and crisis strategies are implemented against the common `generate_signal(bar, kg_context) -> Signal` interface.
- [ ] `MomentumOverlay` runs identically regardless of `--use-graph` setting (true "ungrounded baseline" per existing README semantics).
- [ ] KG-grounded strategies are only activated for a given cycle when the current regime's `ACTIVATED_BY` relationship in the KG sanctions them — matching existing `--use-graph` behavior.
- [ ] Every `Signal` produced by any strategy passes P0 Feature 1 validation before being passed to the overlay stage.
- [ ] Adding a new strategy requires implementing the common interface only — no changes to `event_engine.py`'s control flow.

## Feature 6: Event-Driven Backtest Loop

**Description:** The core simulation loop that, for each timestep, replicates the orchestrator's full sequence — regime determination → strategy signal generation → news/macro overlay application → KG formula merge → fusion → contradiction check — and produces the resulting `Signal` stream plus a trade log for downstream metrics.

### User Stories

- As a **researcher**, I want the backtest's per-timestep sequence to match the live orchestrator's order of operations exactly, so backtest results are a meaningful proxy for live behavior (not just "similar but reordered").
- As a **parity tester**, I want the loop's output to be the exact `Signal` stream that P0 Feature 4 (replay export) can serialize, with no separate translation step.
- As an **operator**, I want a `--disable-news-overlay` / `--disable-macro-overlay` / `--use-graph` flag combination to be fully composable, so any combination of ablation settings can be run from a single CLI invocation.

### Acceptance Criteria

- [ ] For each timestep, the loop executes: regime determination → applicable strategies generate raw signals → news overlay applied → macro overlay applied → KG formula contribution merged → quant/sentiment fusion (70/30) → final `score` computed → contradiction check (`contradiction_blocked`) applied.
- [ ] The default rebalance cadence matches the existing 5-day rebalance behavior from `engine.py`, configurable per run.
- [ ] Contradiction checks use the same `CONTRADICTED_BY` KG relationship logic as the live orchestrator.
- [ ] Every `Signal` emitted by the loop is immediately exportable via P0 Feature 4 without modification.
- [ ] All CLI flags from Features 3 and 5 (`--use-graph`, `--disable-news-overlay`, `--disable-macro-overlay`) can be combined in a single run, and the loop's behavior for each combination is independently testable.
- [ ] A trade log is produced alongside the signal stream, capturing entries/exits sufficient for P2's Profit Factor, Win Rate, and Avg Hold Days metrics (open/close timestamp, ticker, direction, size, entry/exit price).

## Feature 7: Asset-Class & Venue-Aware Fee/Slippage Modeling

**Description:** Per-asset-class (and, where relevant, per-venue) fee and slippage assumptions applied during backtest fills, consistent with the parameters in the main spec's risk table (§6).

### User Stories

- As a **researcher**, I want crypto fills to use Kraken's taker fee (0.26%) and a configurable slippage range, while equity fills use a different assumption, so backtest P&L isn't distorted by a one-size-fits-all cost model.
- As a **capstone author**, I want the backtest's cost model to be explicitly different from (and documented as different from) the eventual IBKR paper-fill behavior (which uses Gateway's simulated fills, per main spec §5.6), so this known asymmetry doesn't get rediscovered as a "bug" later.

### Acceptance Criteria

- [ ] Crypto fills apply Kraken taker fee (0.26%, configurable) plus a configurable slippage assumption (default 0.10–0.25% range).
- [ ] Equity/macro-proxy fills apply a separate, documented fee/slippage assumption distinct from the crypto model.
- [ ] All fee/slippage parameters are configurable via the same `.env`/config source the rest of the system uses — no magic numbers hardcoded into the event loop.
- [ ] The backtest's documentation explicitly notes that this internal fee/slippage model is a *backtest-only* approximation, and that live IBKR paper fills (P6) will use a different mechanism (Gateway-reported fills) — flagged so P8's ablation writeup addresses it.

## Out of Scope for P1

- Metric calculation (Sharpe, Calmar, Profit Factor, Win Rate, Avg Hold Days, Jobson-Korkie) — these consume P1's trade log/signal stream but are P2 deliverables.
- `risk_sim.py` (Python reference RiskEngine) — P2.
- Any C++ code, Redis integration, or live/paper venue connectivity — P3 onward.
- Vectorized-mode parity with the event-driven loop — the existing vectorized `engine.py` is preserved as-is; P1 adds the event-driven mode alongside it, not a reconciliation between the two.
