# P2 — Backtest Metrics & Python Risk Reference (`risk_sim.py`)

**Phase goal:** Extend the metrics layer to match the live system's enriched output contract (Profit Factor, Win Rate, Avg Hold Days alongside existing Sharpe/Calmar/Max DD/JK), and produce a standalone Python reference implementation of the risk-sizing logic (`risk_sim.py`) — extracted from `risk_agent.py` — that both the P1 backtest engine and the future C++ `RiskEngine` (P3) can be validated against. Depends on P0 (contracts) and P1 (signal stream, trade log).

---

## Feature 1: Extended Performance Metrics

**Description:** Add Profit Factor, Win Rate, and Avg Hold Days to the existing metrics module (Sharpe, Calmar, Max DD, Annualised Vol, Jobson-Korkie), computed from the P1 trade log, so backtest output matches the live `BacktestPanel`/`RiskPanel` contract field-for-field.

### User Stories

- As a **researcher**, I want Profit Factor and Win Rate reported alongside Sharpe/Calmar, so I can distinguish "high Sharpe from few large wins" from "high Sharpe from consistent small edges" when comparing strategies.
- As a **frontend consumer**, I want the backtest output JSON to already contain the same fields `BacktestPanel`/`RiskPanel` expect, so no frontend changes are needed when this engine replaces the simpler existing one.
- As a **capstone author**, I want Avg Hold Days reported per strategy/asset-class, so I can characterize each strategy's trading frequency in the writeup (e.g. "momentum holds ~12 days, crisis strategy holds ~2 days").

### Acceptance Criteria

- [ ] Profit Factor is computed as gross profit / gross loss from the P1 trade log; reported as `null` (not `0` or an error) when gross loss is zero, with this convention documented.
- [ ] Win Rate is computed as the fraction of closed trades with positive P&L, reported in `[0.0, 1.0]`.
- [ ] Avg Hold Days is computed as the mean holding period (in days) across closed trades, with a documented behavior for trades still open at backtest end (excluded from the average, and separately reported as "open positions at end").
- [ ] All pre-existing metrics (Total Return, Sharpe, Calmar, Max DD, Annualised Vol, Jobson-Korkie z-stat/p-value/significant) continue to be produced unchanged.
- [ ] The output JSON structure for a backtest run matches the existing `/backtest/run` → `/backtest/status` contract, extended with `profit_factor`, `win_rate`, `avg_hold_days`, plus `equity_curve` and `trade_log` arrays.
- [ ] Metrics can be computed at three levels of granularity: portfolio-wide, per asset-class, and per strategy — selectable without re-running the backtest (i.e. computed from the same trade log via different groupings).
- [ ] For a fixed trade log, repeated metric computation produces identical results (deterministic, no randomness in the metrics layer itself).

## Feature 2: Regime-Conditional & Overlay-Conditional Metric Breakdowns

**Description:** Extend the ablation/breakdown reporting introduced in P1 (regime-conditional Sharpe, overlay ablation flags) so the new metrics (Profit Factor, Win Rate, Avg Hold Days) are available under the same breakdowns, and per-asset-class Jobson-Korkie tests are produced alongside the portfolio-level one.

### User Stories

- As a **researcher**, I want regime-conditional Sharpe *and* Win Rate, so I can see not just "this strategy is profitable in BullMarket" but "it wins more often, or wins bigger, in BullMarket."
- As a **researcher running overlay ablation**, I want the full metric set (including new ones) reported separately for `--disable-news-overlay` / `--disable-macro-overlay` runs vs. baseline, so the marginal contribution of each overlay is visible across all metrics, not just Sharpe.
- As a **multi-asset researcher**, I want per-asset-class Jobson-Korkie significance tests (equity vs. crypto vs. macro proxy) alongside the portfolio-level test, so I can tell whether KG-grounding's edge is concentrated in one asset class.

### Acceptance Criteria

- [ ] For each regime period identified during the backtest, all Feature 1 metrics (not just Sharpe) are computed and reported as a regime-keyed breakdown.
- [ ] Running the same backtest configuration with each overlay independently disabled (per P1 Feature 3 flags) produces a full Feature 1 metric set per configuration, enabling direct before/after comparison across all metrics.
- [ ] Jobson-Korkie z-stat/p-value/significant is computed at portfolio level *and* independently per `asset_class` present in the universe.
- [ ] Breakdown outputs use a consistent key structure (e.g. `metrics_by_regime`, `metrics_by_overlay_config`, `jk_by_asset_class`) documented in the output JSON schema.
- [ ] All breakdowns are derived from a single backtest run's trade log/signal stream where possible — re-running the simulation multiple times is only required for the overlay-ablation comparison (since overlays affect signal generation itself), not for regime/asset-class breakdowns (which are groupings of one run's output).

## Feature 3: `risk_sim.py` — Python Reference Risk Engine

**Description:** Extract the sizing/risk-check logic currently embedded in `risk_agent.py` into a standalone, importable module that takes a Schema v1 `Signal` plus current portfolio state and returns either an `ApprovedOrder` or a rejection — usable by the backtest engine (to simulate realistic position sizing) and as the ground truth for C++ `RiskEngine` parity testing (P3/P7).

### User Stories

- As a **backtest developer**, I want the backtest to size positions using the *same* half-Kelly/position-cap/sector-cap/VaR logic as the live system, so backtest P&L reflects realistic position sizes, not arbitrary fixed-size trades.
- As a **C++ developer (future P3)**, I want a Python reference implementation with a clear input/output contract, so I know exactly what the C++ `RiskEngine` must reproduce — including edge cases like a rejected order or a circuit-breaker halt.
- As a **risk engineer**, I want sector concentration and VaR checks to operate on a portfolio view that can span multiple venues (Kraken + IBKR), even though P2 itself has no live venue connectivity, so the *logic* is venue-agnostic from day one and P6 doesn't require a risk-logic rewrite.

### Acceptance Criteria

- [ ] `risk_sim.py` exposes a function/class taking a Schema v1 `Signal` and current portfolio state (positions, NAV, sector exposures, drawdown-from-peak) and returning either a Schema v1 `ApprovedOrder` or a structured rejection with reason.
- [ ] Half-Kelly position sizing uses `AGENT_KELLY_FRACTION` from config (currently 0.5 cap), producing `kelly_fraction` within the bounds defined in P0 Feature 2.
- [ ] Position sizing respects `AGENT_MAX_POSITION_PCT` (per-instrument NAV cap) and `RISK_MAX_SECTOR_PCT` (per-sector NAV cap, for asset classes where sector applies per main spec §6).
- [ ] Parametric VaR contribution is computed at `RISK_VAR_CONFIDENCE` (99%); an order is rejected if `var_contribution_pct` would exceed `RISK_MAX_VAR_PCT`.
- [ ] A circuit-breaker check halts order approval (returns rejection for all signals) once portfolio drawdown-from-peak exceeds `AGENT_MAX_DRAWDOWN_HALT`, matching the live system's behavior.
- [ ] Sector concentration and VaR checks operate on portfolio state that is structured to span multiple venues (i.e. the function signature accepts a unified cross-venue position list), even though P2's only caller is the single-venue-agnostic backtest.
- [ ] Every `ApprovedOrder` produced by `risk_sim.py` passes P0 Feature 2 validation, including the IBKR-paper-only constraint (trivially satisfied in P2 since no orders carry `venue=ibkr, mode=live`).
- [ ] All five threshold values (`AGENT_KELLY_FRACTION`, `AGENT_MAX_POSITION_PCT`, `RISK_MAX_SECTOR_PCT`, `RISK_VAR_CONFIDENCE`, `RISK_MAX_VAR_PCT`, `AGENT_MAX_DRAWDOWN_HALT`) are read from the same `.env` source as the live `risk_agent.py` — no duplicated/hardcoded copies.
- [ ] For a fixed `(signal, portfolio_state)` input pair, `risk_sim.py` produces a deterministic output — required for P3/P7 parity diffing to be meaningful.

## Feature 4: Backtest Integration of `risk_sim.py`

**Description:** Wire `risk_sim.py` into the P1 event-driven loop so backtest position sizes, sector caps, VaR rejections, and circuit-breaker halts are realistic — replacing any placeholder fixed-size trade assumption from P1.

### User Stories

- As a **researcher**, I want a backtest where a strategy's signal can be rejected by risk checks (e.g. VaR cap breached), and the trade log reflects that rejection, so reported performance doesn't assume infinite risk capacity.
- As a **capstone author**, I want backtest runs that hit the drawdown circuit breaker to show a visible "halted" period in the equity curve/trade log, so the circuit breaker's effect on outcomes is part of the reported results, not invisible.

### Acceptance Criteria

- [ ] Each `Signal` produced by the P1 loop is passed through `risk_sim.py` before becoming a trade; rejected signals are recorded (with rejection reason) but do not generate trades.
- [ ] The trade log (P1 Feature 6) reflects risk-sized quantities/notionals from `risk_sim.py`'s `ApprovedOrder`, not strategy-suggested raw sizes.
- [ ] When the circuit breaker triggers mid-backtest, all subsequent signals are rejected (logged as "halted") until drawdown recovers below threshold (matching live semantics), and this halted period is identifiable in the output (e.g. a `halted_periods` array alongside `equity_curve`).
- [ ] Re-running a backtest with `AGENT_MAX_DRAWDOWN_HALT` set to an unreachable value (e.g. 100%) produces a result identical to one with the circuit-breaker logic removed — confirming the breaker only affects outcomes when actually triggered.
- [ ] Rejection reasons recorded during backtest use the same vocabulary `risk_sim.py` returns (Feature 3), so downstream tooling doesn't need a translation layer.

## Out of Scope for P2

- C++ `RiskEngine` implementation — P3. P2 produces the Python reference it must match.
- Any actual cross-venue portfolio data (real IBKR/Kraken positions) — P2's "cross-venue-shaped" portfolio state (Feature 3) is a structural readiness requirement, not a live integration.
- Redis/replay runner wiring for parity testing — P3/P7. P2 only needs to produce deterministic, diffable output.
- Frontend changes — none required; output contract is designed to be a drop-in extension of the existing `BacktestPanel`/`RiskPanel` JSON.
