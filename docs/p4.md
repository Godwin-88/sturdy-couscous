# P4 — C++ ExecutionEngine (Paper Mode) + Audit Log + Event Publisher

**Phase goal:** Build the execution layer that consumes `ApprovedOrder` objects from the P3 `RiskEngine`, simulates fills in paper mode, persists results to the existing Postgres tables, and publishes events to the existing `/ws/events` Redis channel — so the React dashboard requires zero changes. No venue connectivity yet (no Kraken REST, no IB Gateway); P4 proves the execution/audit/event pipeline end-to-end using simulated fills only. Depends on P3 (`RiskEngine` producing `ApprovedOrder`).

---

## Feature 1: Paper Fill Simulation

**Description:** A fill simulator that takes an `ApprovedOrder` and produces a simulated execution result (fill price, timestamp, fees) using the asset-class/venue-aware fee/slippage model defined in P1 Feature 7 — the production-side counterpart to the backtest's fill model.

### User Stories

- As an **execution developer**, I want paper fills in production to use the *same* fee/slippage assumptions as the backtest's fill model (for crypto/Kraken), so a strategy's live paper performance is directly comparable to its backtest performance.
- As a **capstone author**, I want the production paper-fill model to be the identical implementation (not a reimplementation) of the backtest's — sharing the model, not duplicating it, eliminates a class of "backtest vs live divergence" questions.
- As an **operator**, I want every simulated fill to carry a timestamp and price that's traceable to a real market data point (not an arbitrary constant), so paper P&L reflects real market conditions even though no real order was sent.

### Acceptance Criteria

- [ ] For `venue = kraken`, paper fills apply the same fee (0.26% taker, configurable) and slippage assumptions used in P1 Feature 7, sourced from the same `.env` configuration values.
- [ ] Fill price is derived from a real market price at (or near) order time — the simulator requires a current/recent price feed input, not a hardcoded value.
- [ ] Fill simulation produces a structured result: `fill_price`, `fill_timestamp`, `fee_usd`, `slippage_usd`, distinct from the `ApprovedOrder`'s decision-time `notional_usd`.
- [ ] The fee/slippage *parameters* (not necessarily the code) are demonstrably the same values as P1 Feature 7 — i.e. changing `.env` once affects both backtest and paper-execution fills identically.
- [ ] `venue = ibkr` orders are explicitly **not** handled by this simulator (deferred to P6, where IBKR Gateway provides its own simulated fills per main spec §5.6) — P4's fill simulator only activates for `venue = kraken`.

## Feature 2: Position & Portfolio State Tracking

**Description:** In-memory (and Postgres-persisted) tracking of open positions, NAV, and drawdown-from-peak, updated after each simulated fill — providing the live "current portfolio state" that `RiskEngine` (P3) needs as input for its next decision.

### User Stories

- As a **risk engineer**, I want the portfolio state fed into `RiskEngine` for cycle N+1 to reflect the fills from cycle N, so position/sector/VaR caps are evaluated against reality, not stale state.
- As an **operator**, I want NAV and drawdown-from-peak computed continuously as fills occur, so the circuit breaker (P3 Feature 5) can trigger based on live state, not a periodic recalculation.
- As a **future multi-venue operator**, I want position state structured per-venue internally but aggregable into the cross-venue view `RiskEngine` expects (per P3 Feature 3's design), even though P4 only has Kraken positions.

### Acceptance Criteria

- [ ] After each simulated fill, the position for that `(ticker, venue)` is updated (opened, increased, decreased, or closed) and NAV/drawdown-from-peak are recomputed.
- [ ] The updated portfolio state is the exact input shape `RiskEngine` (P3) expects for its next `Signal` evaluation — no translation layer between "what P4 tracks" and "what P3 consumes."
- [ ] Position state is structured with an explicit `venue` field per position, even though all positions in P4 have `venue = kraken` — this is a structural requirement, not a behavioral one (mirrors P3 Feature 3's forward-looking design).
- [ ] Portfolio state is persisted to Postgres (`positions`, `portfolio_state` tables) after every update, surviving a service restart without loss of current state.
- [ ] On service startup, portfolio state is reconstructed from the most recent Postgres state (not reset to empty/zero), so a restart doesn't erase the circuit breaker's drawdown-from-peak history.

## Feature 3: Postgres Audit Log Writer

**Description:** Writes an immutable record of every `ApprovedOrder`, fill result, and rejection (from `RiskEngine`) to the existing `order_audit` table — preserving the existing schema so no migration or frontend change is required.

### User Stories

- As a **compliance-minded operator**, I want every order decision — approved, filled, or rejected — written to an immutable audit log, so I can reconstruct "what did the system decide and why" for any point in time.
- As a **maintainer**, I want this writer to use the *existing* `order_audit` table schema (`infra/postgres/init.sql`), so P4 is additive infrastructure, not a schema migration.
- As a **parity tester**, I want rejected signals (from `RiskEngine`'s P3 Feature 5/6 rejection paths) also logged, with their rejection reason, so "the system correctly chose not to trade" is as auditable as "the system traded."

### Acceptance Criteria

- [ ] Every `ApprovedOrder` produced by `RiskEngine` results in a row in `order_audit` (existing schema), including the full `risk_checks` breakdown and `kelly_fraction`/`var_contribution_pct`.
- [ ] Every fill result (Feature 1) is associated with its originating `order_audit` row (e.g. via `order_id`), recording `fill_price`, `fill_timestamp`, `fee_usd`, `slippage_usd`.
- [ ] Every rejected `Signal` (failed risk check or circuit-breaker halt, from P3) is logged with its `cycle_id`, `strategy`, `ticker`, and rejection reason — using the existing table or a documented minimal addition if `order_audit` cannot represent "no order was created."
- [ ] Audit log writes are append-only — no `UPDATE`/`DELETE` operations on historical rows from the C++ engine.
- [ ] If a Postgres write fails (connection issue, etc.), the engine logs the failure loudly and does **not** silently proceed as if the audit succeeded — a write failure is itself an event worth surfacing.

## Feature 4: `/ws/events` Publisher

**Description:** Publishes execution events (order approved, filled, rejected, circuit-breaker state change) to the existing Redis `/ws/events` pub/sub channel, in the same message format the Python `agent-worker` currently produces — so `AgentLog`, `PnLDashboard`, and `RiskPanel` work unmodified.

### User Stories

- As a **frontend consumer**, I want events published by the C++ engine to be indistinguishable in format from events the Python agent currently publishes, so `AgentLog`/`PnLDashboard`/`RiskPanel` require zero code changes.
- As an **operator**, I want to see paper fills, rejections, and circuit-breaker halts appear in the dashboard in real time, exactly as I would with the current Python-only system.

### Acceptance Criteria

- [ ] The C++ engine connects to the existing Redis instance and publishes to the existing `/ws/events` channel (or whichever channel the current frontend subscribes to — confirmed against current `agent-worker` code before implementation).
- [ ] Message format (field names, types, structure) for "order approved," "order filled," "order rejected," and "circuit breaker halted/recovered" events matches the existing Python-published event format exactly.
- [ ] With the C++ engine running standalone (P3's `RiskEngine` + P4's `ExecutionEngine`, fed by a manual/test signal stream — no live agent-worker needed for this check), the existing frontend dashboard displays these events correctly with no frontend code changes.
- [ ] Circuit-breaker state transitions (P3 Feature 5) are published as distinct events, so `RegimePanel`/`AgentLog` can show "HALTED" / "RECOVERED" states originating from the C++ engine.

## Feature 5: Standalone Service Wiring (`main.cpp`)

**Description:** A runnable C++ binary that ties Features 1–4 together into a single service process — accepting a stream of `Signal` objects (initially via a simple file/stdin feed for testing, since Redis subscription is P5), running them through `RiskEngine` → `ExecutionEngine`, and producing audit/event output.

### User Stories

- As a **maintainer**, I want a single binary I can run that demonstrates the full P3→P4 pipeline working end-to-end on a test signal stream, before P5 wires it to live Redis.
- As an **operator**, I want this binary configured entirely via the same `.env` the rest of the system uses, so there's no separate C++-only configuration surface to maintain.

### Acceptance Criteria

- [ ] `main.cpp` builds to a single binary that, given a file of Schema v1 `Signal` JSON lines (e.g. reusing P0 Feature 4's export format) and an initial portfolio state, processes each signal through `RiskEngine` → `ExecutionEngine`, writing audit rows and publishing events for each.
- [ ] All configuration (`.env` values from P3 Features 2–5, plus any new fee/slippage/Postgres/Redis connection settings) is read from the same `.env` file used elsewhere — confirmed by running the binary against the project's actual `.env` without modification.
- [ ] Running the binary against a known P0-Feature-4-exported signal stream produces Postgres rows and Redis events that can be independently verified against expected values (a fixture-based end-to-end test).
- [ ] The binary can be built and run inside a Docker container using the multi-stage build described in the main spec (§5.2), as a standalone `risk-engine` service — even though Compose wiring to live `agent-worker` happens in P5.
- [ ] Service startup correctly reconstructs portfolio state from Postgres (Feature 2) before processing the first signal in the input stream.

## Out of Scope for P4

- Redis *subscription* to live orchestrator signals — P4 consumes a file-based signal stream; live Redis pub/sub wiring to `agent-worker` is P5.
- Kraken REST live/paper order submission — P4's "paper" is purely simulated (Feature 1); actual Kraken API connectivity (even in paper mode, if Kraken offers one) is not required here. Confirm: does Kraken's paper trading require API calls at all, or is GraphAlpha's "paper mode" entirely internal simulation? If the latter, P4 *is* the complete paper-execution story for Kraken and no further work is needed in later phases for Kraken paper.
- IBKR / IB Gateway — P6.
- Docker Compose integration with the live `agent-worker` service — P5.
