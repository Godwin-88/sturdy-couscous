# P7 — Kraken Live Trading + Live-Mode Parity Validation

**Phase goal:** Extend the existing Kraken paper path (P4) to support real live order submission, gated by `KRAKEN_TRADING_MODE`, and validate — with real capital at stake — that the C++ engine's live behavior matches everything proven in paper mode across P3–P6. IBKR remains paper-only throughout this phase; it is not touched. This is the highest-stakes phase in the plan: the first time GraphAlpha risks real money, so validation gates are deliberately heavier than any prior phase.

---

## Feature 1: Kraken REST Live Client

**Description:** Extend `KrakenAdapter` (paper-only since P4) with real REST API connectivity for live order submission — HMAC-SHA512 request signing, `/0/private/AddOrder` calls, and live order status polling — activated only when `KRAKEN_TRADING_MODE=live`.

### User Stories

- As an **execution developer**, I want the live order-submission code path to be a true extension of the paper path (same adapter, same interface), not a parallel implementation, so any bug fixed in paper mode automatically benefits live mode and vice versa.
- As a **security-conscious operator**, I want Kraken API keys read from `.env` and never logged, written to disk in plaintext, or included in any audit/event payload, so a log leak can't become a capital-loss incident.
- As a **risk-averse operator**, I want it to be impossible to accidentally submit a live order while believing I'm in paper mode, so a config typo doesn't become a real trade.

### Acceptance Criteria

- [ ] `KrakenAdapter` gains live-mode functionality: HMAC-SHA512 request signing using API key/secret from `.env`, `/0/private/AddOrder` submission, and order status polling via `/0/private/QueryOrders` (or equivalent).
- [ ] Live-mode activation requires `KRAKEN_TRADING_MODE=live` **and** a separate explicit confirmation step at startup (e.g. the engine logs the active mode loudly on boot, and/or requires a non-default flag) — no single silent config value should be sufficient to flip from paper to live.
- [ ] API keys/secrets are never written to logs, audit tables, or `/ws/events` payloads — verified by inspecting actual log/audit output during a test run, not just by code review.
- [ ] In paper mode, no code path in `KrakenAdapter` makes a real authenticated API call to Kraken — paper and live are structurally separated within the adapter, not merely parameter-gated at the last line before the request.
- [ ] A live order submission failure (API error, rejected order, network failure) is handled explicitly — logged with full context, reflected in `/ws/events` and `order_audit`, and does **not** crash the service or leave portfolio state in an inconsistent position (e.g. recorded as filled when it wasn't).
- [ ] Existing P4 paper-mode behavior (fill simulation, fee/slippage model) is unchanged and continues to pass its existing tests after this feature is added.

## Feature 2: Live Order Reconciliation

**Description:** Logic to reconcile GraphAlpha's internal view of "what orders are open/filled" against Kraken's actual account state — necessary because live orders can fill partially, fail silently on the exchange side, or be affected by exchange-side issues that don't exist in a simulated paper environment.

### User Stories

- As an **operator**, I want the system's recorded positions to match my actual Kraken account balance, so a discrepancy (partial fill, failed order, manual intervention) doesn't silently corrupt the risk engine's view of NAV/drawdown.
- As a **risk engineer**, I want a reconciliation mismatch to halt new order submission until resolved, since sizing decisions based on a wrong NAV are exactly the kind of error the circuit breaker (P3 Feature 5) exists to prevent — and a stale/wrong NAV is a blind spot the circuit breaker can't see on its own.

### Acceptance Criteria

- [ ] On startup and at a regular interval (configurable, e.g. every N minutes), `risk-engine` queries Kraken's actual account balance/open orders and compares against its internally tracked Kraken positions (from `positions`/`portfolio_state`).
- [ ] A detected mismatch beyond a configurable tolerance is logged loudly, surfaced via `/ws/events` (so it's visible on the dashboard), and triggers a halt on new Kraken live order submission until the mismatch is resolved or manually acknowledged.
- [ ] Reconciliation does not affect IBKR positions or the IBKR halt state — a Kraken reconciliation issue halts Kraken live trading specifically, not the entire cross-venue system, unless it also breaches the cross-venue drawdown threshold independently.
- [ ] Partial fills are correctly reflected in position size (not rounded to "filled" or "not filled") and reconciled against Kraken's reported partial-fill state.
- [ ] A manual "acknowledge and resync" operation exists (documented procedure, even if it's a CLI command rather than a UI button) for an operator to confirm a reconciliation discrepancy has been investigated and resolved, clearing the halt.

## Feature 3: Live-Mode Parity Validation (Paper vs. Live Comparison)

**Description:** A structured validation period where Kraken live trading runs at minimal size/risk alongside continued paper-mode operation, comparing decisions and outcomes before live trading is trusted at full intended size — analogous to P5 Feature 4's shadow mode, but for the paper→live transition rather than Python→C++.

### User Stories

- As a **risk-averse operator**, I want to validate live execution behavior with small real capital before committing the full intended position sizes, so any live-specific issue (latency, slippage being worse than modeled, partial fills behaving unexpectedly) is discovered cheaply.
- As a **capstone author**, I want this validation period's results documented, so "the system was validated live before scaling" is evidence in the writeup, not just an assertion.

### Acceptance Criteria

- [ ] A configurable position-size scaling factor (e.g. `LIVE_VALIDATION_SCALE_PCT`, distinct from `AGENT_MAX_POSITION_PCT`) allows running live trading at a fraction of normal sizing during this validation period, without changing any risk-decision logic itself — only the final order quantity is scaled down.
- [ ] For each live trade during validation, the actual fill price/timing is compared against what the same signal would have produced in paper mode (using the P4 paper-fill simulator on the same signal, for comparison purposes only — not affecting the real order).
- [ ] Discrepancies between live and paper-simulated outcomes (worse slippage than modeled, fill timing differences, fee differences) are logged in a structured, reviewable format.
- [ ] A documented exit criterion exists for this validation period (e.g. "N live trades with no unexplained discrepancy beyond tolerance X") before `LIVE_VALIDATION_SCALE_PCT` is removed/set to 1.0 for full-size live trading.
- [ ] The validation period's results (discrepancy log, exit-criterion satisfaction) are written up as a documented artifact — this directly feeds the main spec §8 P8 capstone deliverable.

## Feature 4: Live-Mode Circuit Breaker & Kill Switch

**Description:** Strengthen the existing circuit breaker (P3 Feature 5) for live-money conditions, and add an explicit, fast-acting manual kill switch independent of the automated drawdown breaker — because live trading needs a "stop everything now" mechanism that doesn't depend on the system correctly computing drawdown first.

### User Stories

- As an **operator**, I want a single, simple action to immediately stop all new live order submission (Kraken) regardless of system state, so if something looks wrong — even something the automated checks haven't caught — I can intervene without needing to understand the C++ engine's internals under pressure.
- As a **risk-averse operator**, I want the existing `AGENT_MAX_DRAWDOWN_HALT` circuit breaker to apply to live trading with the same semantics validated in paper mode (P3 Feature 5, P4, P6), so live behavior under drawdown isn't a new, unvalidated code path.

### Acceptance Criteria

- [ ] A manual kill switch (e.g. an `.env` flag checked on a short polling interval, or a dedicated Redis key `risk-engine` checks every cycle) immediately halts new Kraken live order submission when set, independent of drawdown/VaR/position-cap logic.
- [ ] The kill switch takes effect within one signal-processing cycle of being set — not requiring a service restart.
- [ ] The existing drawdown circuit breaker (P3 Feature 5) is confirmed, via the Feature 3 validation period, to behave identically for live orders as it did in paper mode — no live-specific exception or different threshold.
- [ ] When either the kill switch or the drawdown breaker is active, this state is prominently visible on the dashboard (extending P4 Feature 4's halt-state event), distinguishing "manual kill switch" from "automated drawdown halt" so the operator knows which one is active and why.
- [ ] Re-enabling live trading after either halt requires an explicit action (not automatic recovery) — confirmed by testing that simply having drawdown recover, or unsetting the kill switch, does not silently resume live order submission without an additional confirming step.

## Out of Scope for P7

- IBKR live trading — explicitly and permanently out of scope per the main spec's stated phase boundaries unless a future spec revision changes this; P7 touches Kraken only.
- Removing/scaling back paper mode — paper mode continues running for ongoing research/comparison purposes after live trading is enabled; this is not a paper→live cutover that retires paper mode.
- Any change to position sizing logic itself (Kelly/VaR/caps) — Features 1–4 are about *execution* and *safety mechanisms* for live trading, not new risk-sizing behavior. If live trading reveals the sizing logic itself needs adjustment, that's a change to `risk_sim.py`/`RiskEngine` requiring its own re-validation through P2/P3's parity suite, not a P7 change.
- Tax, regulatory, or brokerage-compliance considerations — explicitly noted as outside this spec's scope; the user should confirm independently that live automated trading via Kraken is permissible under their account terms and applicable regulations before this phase goes live.

## Dependencies / Inputs Needed Before P7 Can Be Marked Done

1. P3–P6 complete and stable, including at least the Kraken-relevant portions of P6's cross-venue validation (Feature 4 of P6) — live trading shouldn't be the first real test of cross-venue NAV/drawdown logic.
2. Kraken account funded and API keys provisioned with appropriate (and minimal necessary) permissions — trade-only, no withdrawal permission, as a baseline security practice, confirmed before Feature 1 implementation.
3. An explicit, operator-set decision on `LIVE_VALIDATION_SCALE_PCT`'s starting value and Feature 3's exit criterion, made deliberately in advance rather than improvised once live trades start appearing.
4. Confirmation that the operator has reviewed Kraken's own terms of service regarding automated/algorithmic trading, and any applicable personal tax-reporting obligations for realized gains — a one-time check, not a recurring spec requirement, but a precondition the user should clear before P7 begins given this spec cannot itself provide legal/tax advice.
